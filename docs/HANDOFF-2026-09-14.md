## 2. The four foundation defects — fix these before anything else

They are shared. Nine of the thirteen items above are blocked by them, and
fixing them once repairs every area. Do not start feature work first.

**F1 — one predicate kills every batch-cost posting.**
`apps/api/src/modules/finance/journal/gl-posting.service.ts:61`
```ts
conditions.push((value ? or(eq(col, value), isNull(col)) : isNull(col))!);
```
"Caller supplied nothing" is read as "mapping must be NULL here". Verified:
`gl_mapping_master` = 29 rows, `val_wild=0 nob_wild=0 lob_wild=0 cat_wild=26`.
`postBatchCostEntry()` never passes a valuation method → **all 11 call sites
400**. Mortality, overhead, impairment, every variance, all 9 `BIO_*` events.
`postInventoryLedgerEntry` survives only for the 19/31 FIFO items.
Also pinned: 3 mappings pin `item_category_id` to Finished Swine Feeds (so
consuming a medicine against a batch 400s), and all 13 `BIO_*` pin
`stage_id=GESTATION`. Both from `seed-demo-detail.ts:245,248,256`.
**Fix:** treat absent value as *match anything*, plus clear the over-pins.

**F2 — the ledger invents inventory.**
`apps/api/src/modules/inventory/inventory-ledger/inventory-ledger.service.ts:205-245`
When FIFO runs dry it mints `max(shortfall*100, 10000)` units at
`standard_cost || 25` as `AUTO-STOCK-REPLENISH` / `OPENING`. No NODE_ENV guard,
no flag — **would fire in production**. It fired during the audit (10,000 vials
of Penicillin G). Shows on Stock Balance, the first screen in the Inventory nav.
**Fix:** refuse the issue instead, or gate it behind an explicit demo flag.

**F3 — post-then-record with no transaction and no reversal.**
Same shape in `approveUnscheduledHealth`, `postEntry`, and the Goods Receipt
post loop. Stock commits, the record that explains it is written after and can
fail. No `reverseEntry` exists anywhere in the inventory module.
Related: `postEntry` calls `addTransaction` **before** the upsert, so correcting
today's feed 4.6→5.0 issues 5.0 **on top of** the 4.6.

**F4 — nothing in the write path has ever run.**
```

inventory_ledger     6 rows — document_type='BATCH' on 0
journal_header       5 rows — all from seed-demo-full-coverage.ts:399
batch_daily_data     1 row  — DESCRIPTIVE mortality 0.000000, posted=0
batch_cost_variance  0 rows — nothing has ever closed
```
This is why 582 tests pass while features do not work. **After F1–F3, post one
GRN, one issue, one transfer, one adjustment and one batch consumption through
the API and read MySQL.** That is the only proof. Expect it to surface more.

## 7. Running the app — and the memory rule that matters most

**This is an 8 GB MacBook Air that swaps hard. Rishi works in Brave and VS Code
alongside you.**

- **Leave the dev servers running.** Stop them only when memory is genuinely red.
  Check, do not guess: `top -l 1 -n 0 | grep PhysMem` and `sysctl vm.swapusage`.
- **Never run `pkill`.** It has killed a whole session here. Stop a server by a
  PID confirmed with `lsof -ti :PORT`.
- Never run `nx serve api` + `nx dev web` + a browser at once.
- Cap heap on anything heavy: `NODE_OPTIONS="--max-old-space-size=1024"`.
- Prefer curl + direct MySQL over a browser. It costs nothing and proves more.

**`nx serve api` does NOT rebuild on source change** — `api:build` is a bare
`webpack-cli build` with no `--watch`, and the node executor does not respawn.
Editing API source changes nothing the running API serves. To see a change live:

```bash
pnpm nx build api --configuration=development
kill $(lsof -ti :2877 -sTCP:LISTEN)
cd apps/api && NODE_OPTIONS="--max-old-space-size=1024" \
  nohup node --env-file-if-exists=.env dist/main.js > /tmp/api.log 2>&1 &
```

Running the bundle directly is also far lighter — **83 MB vs 264 MB** for
`nx serve`. `apps/web` is the opposite: `next dev` hot-reloads, leave it alone.

Currently up: API `:2877` (bundle, ~83 MB), web `:3002` (`next dev`, ~102 MB).

## 9. How to work here

- **Drive the running app. Reading the code is not verification.** Every defect
  that mattered in this project passed its tests and read correctly. F4 is the
  proof: 582 green tests over a write path that has never executed.
- **Check the database after a write.** A 200 is not proof the row is right.
- **Test sort by comparing asc against desc.** A sorted and an unsorted list are
  identical from a status code — that is how two masters hid a dead sort.
- **Never claim something is missing from an exact-name grep.** Search by
  fragment and concept, and say which spellings you tried. Four false negatives
  in one session came from this.
- **Never invent client data.** No placeholder names, no "typical" values. There
